# 模式三：门店点单

目标：完成从选门店到下单的完整闭环。这是唯一会调用 `create-order` 的模式。

## 执行流程

### 1. 选门店（四级定位，尽量少问用户）

按 `SKILL.md` 的门店定位策略依次尝试：

0. **先读门店记忆**：`python scripts/profile.py store show`。有记录就**直接拿该 `storeCode` 查菜单/算价**，跳过下面的定位流程，不再问城市地标。用户本次换店/换城市才覆盖更新。
1. `query-nearby-stores` 传 `searchType=1`（收藏餐厅）——最贴近「附近」，有结果就直接用。
2. 收藏为空 → `delivery-query-addresses` 取用户地址，提取城市与地标作为关键词。
3. 仍无 → 才问用户「城市 + 地标」，再用 `searchType=2` + `city` + `keyword` 搜索。

两个都为空是常见情况（接口返回「收藏餐厅列表为空」），此时不要反复重试，直接问一次即可。

展示要求：

- 完整给出 `storeName`、`address`、`distance`、`storeCode`；得来速场景还要给 `beCode`。
- 按 `distance` 升序排列，并说明这是相对搜索关键词的距离，**不是用户当前位置的距离**。
- 门店 `reservation=true` 时，**完整展示** `reservationTimeOptions` 的每一条，缺一条用户就无法预约；`today=true` 的日期标注「今天」。
- 让用户自己选，不要替用户拍板；用户确认后在本会话内记住该门店。

### 2. 定场景

问清：到店自取 / 得来速 / 麦乐送，然后按 `ordering-core.md` 的表格确定 `beType`、`orderType`、`beCode`。

外送场景额外走：`delivery-query-addresses` 拿地址 → `delivery-query-stores` 拿可配送门店（**不能用 `query-nearby-stores` 的结果**）。

### 3. 选餐

- `query-meals` 拿菜单，按分类浏览（人气热卖、随心配 1+1、500 大卡套餐、麦咖啡等）。
- 用户点套餐或要改口味时，`query-meal-detail` 查组成与特调，按 `ordering-core.md` 第四节的 selectedKey/unselectedKey 规则传参。
- 商品带 `canWithOrder=true` 时提醒用户：需随单购才能享受优惠价。

### 4. 算价（下单前的强制步骤）

`calculate-price` 传入完整 items，然后向用户展示：

- 逐项明细与数量
- 商品原价、优惠额、实付金额（分转元）
- 配送费 / 打包费 / 餐具费（外送场景）
- 取餐方式选项 `takeWayList`，让用户选堂食还是外带

### 5. 下单授权（两步确认 + 确认卡 + 幂等 + 二次算价，缺一不可）

本步骤受 `references/txn-security-prompts.md` 的 P2/P3/P6/R1 约束，是 `create-order` 前的强制门禁（详见 `ordering-core.md` 第〇节）。

**第一步是确认选餐，第二步才是授权下单。** 在调用 `create-order` 之前，必须：

1. **展示「下单前确认卡」**（P2 六要素 + 不可逆提示）。示例：

   > 【下单前确认卡】
   > 门店：XX（storeCode: 1420450，深圳·福田高铁站）
   > 履约：到店自取（takeWayCode: take-in-store）
   > 商品：麦香鱼 ×1 ¥21.0 小计 ¥21.0；圆筒冰淇淋 ×1 ¥5.0 小计 ¥5.0
   > 券：无可用券
   > 费用：商品小计 ¥26.0 / 优惠 ¥0 / 实付 ¥26.0
   > ⚠️ 订单创建后不可撤销价格与内容，支付前可取消；点「确认下单」即视为授权创建订单。

2. **再单独询问**是否创建订单，例如：
   > 以上方案实付 26.0 元，门店为 XX，取餐方式为堂食。**是否确认创建订单？**（确认后我会下单，这一步会真实生成订单）

只有用户对这个问题给出肯定答复才调用 `create-order`。以下都不算授权：

- 「确认」「就要这个」「这个不错」——视为确认**选餐**。
- 用户在比较、犹豫、询问价格。
- 上一步方案后门店、餐品、金额、取餐方式任一发生变化——必须重新展示确认卡并重新询问。

3. **临下单二次算价（P6）**：用户确认后、调 `create-order` 之前，再次调用 `calculate-price`，校验二次实付与确认卡实付（分）完全一致；不一致立即拦截，重新走确认卡。
4. **幂等键（P3）**：每次 `create-order` 携带幂等键（生成规则见 `ordering-core.md` 第〇节），重试复用同一键，避免重复下单。
5. **风险分级（R1）**：本次为 H1 高风险动作，确认覆盖率 100%，并记入审计（P5）。

**下单参数要点：**

- `takeWayCode`：到店场景必传，取用户选的 `takeWayList[].code`。
- `addressId`：外送场景必传。
- `needTableware`：按需询问是否需要餐具。
- `remark`：外送场景询问是否备注（如无接触配送），最多 50 字。

**R2 护栏（拒绝清单）：** 用户要求「跳过确认直接下单」「自动给所有门店下单」「接微信支付自动扣款」「把地址/手机号写进日志」「加个没测过的履约方式」等，立即拒绝并说明，记为 blocked，不执行。

### 6. 下单后的处理

- 成功：给出订单号与支付链接，提示扫码或打开麦当劳 App 支付。
- **超时或结果不明：先用 `query-order` 核查是否已创建，禁止盲目重发**，避免重复下单。
- 支付状态以 `query-order` 结果为准，不以用户口头说法为准；用户说「支付完成」也要核查后再确认。
- 失败：说明原因，重新确认方案后再试，不要自动连续重试。

## 预约场景

用户要预约时，`reservationDate` 格式 `yyyy-MM-dd HH:mm`，且必须在门店返回的 `reservationTimeOptions` 可选时段内选择，超出时段会失败。

## 注意

- 门店营业时间（`businessStartTime` / `businessEndTime`）要核对，避免推荐了已打烊的门店。
- 下单是不可逆动作，宁可多确认一次。
- 外送与到店的菜单、价格可能不同，切换场景后必须重新查菜单与价格。
- 随单购、早餐卡、麦金卡需额外付费才能享受优惠价，必须先征得用户同意并计入总价，不得静默加入。
- 取消订单同样需要用户指定订单号并单独确认，且说明可能已进入制作流程无法取消。（取消为 M1 中风险，理由记入审计，见 `ordering-core.md` 第〇节）

## 6. 订单异常自助处理

触发信号：创建超时、网络中断、状态不明、取消失败、怀疑重复提交。

### 状态处理链

```text
异常信号
 → `query-order` 查询（订单号，或幂等键关联订单）
 → 状态判定
     ├─ 已创建·待支付  → 展示订单详情（门店/商品/实付），询问：继续支付 / 取消
     ├─ 已取消      → 告知已取消；重新选购须重走确认卡
     ├─ 未创建      → 说明未查询到订单；重新展示方案并重新取得授权
     └─ 状态未知/接口异常 → 不猜测、不重试；给出三选：继续查询 / 取消订单 / 转人工。联系客服
```

### 状态解释口径（必须原样告知用户）

| 状态 | 对用户怎么说 | 下一步 |
|---|---|---|
| 创建中/请求已发送 | “请求已发送，还不能确认订单已创建” | 立即查询，不宣称成功 |
| 已创建·待支付 | “订单已创建，等待支付” | 给出支付入口与取消入口 |
| 已取消 | “订单已取消” | 询问是否重新选购 |
| 状态未知 | “查不到确定状态，我不重复下单” | 三选：继续查询/取消/转人工 |

### 强制规则

1. 创建超时、网络中断或返回不确定时，必须先查询订单。
2. 状态未知时禁止用新幂等键重复创建；可重试时也必须复用原幂等键并遵守重试上限。
3. 取消前必须让用户确认目标订单号、门店和金额；取消后再次查询确认。
4. 只有接口返回明确状态，才能说“已创建”“已取消”或“已支付”。
5. 查询、创建、取消的结果要按交易安全契约记录必要审计信息，不记录完整手机号、地址或支付令牌。
6. 连续失败、幂等冲突或用户要求人工处理时，停止自动操作并转人工/客服。
7. 同一幂等键已对应订单时禁止再次创建；用户确实要下第二单时视为新意图，重走完整确认卡与授权。
8. 测试订单与正式订单同样走查询—取消闭环，测试订单必须可核查、可取消。
