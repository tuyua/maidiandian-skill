# 模式一：省钱凑单

目标：在预算内给出推荐方案。**默认是「预算内吃得更丰富」**，用户要求省钱时切换为「尽量少花钱」。

## 一、两个目标

| 目标 | 触发条件 | 做法 | 结果特征 |
|---|---|---|---|
| 丰富优先（默认） | 未说明偏好，或说「吃得好点」「丰富点」「预算内随便配」 | 先满足人数与结构，再在预算内增加种类与分量 | 实付接近预算，种类更多 |
| 低价优先 | 明确说「尽量少花钱」「省钱优先」「便宜就行」 | 满足需求后不再加购，把实付降到最低 | 实付更低，余额更多 |

切换目标时必须向用户说明差异，不要静默改变推荐逻辑。

## 二、执行流程

### 1. 收集要素（缺什么问什么，一次问完）

- **预算**：实付上限。
- **人数**：决定主食份数，是丰富优先的基础约束。
- **用餐方式**：到店自取 / 得来速 / 麦乐送（决定 beType）。
- **门店**：没说就查附近门店让用户选。
- **偏好与忌口**：是否需要饮品、有无忌口、是否控热量。

只问缺失项，用户已给出的不再确认。

### 2. 拉取真实数据

按 `ordering-core.md` 的链路：`query-nearby-stores` → `query-meals` → `available-coupons` 与 `query-my-coupons`。

### 3. 先满足需求，再谈丰富

推荐次序固定：

1. **人数份数**：主食份数先满足人数（两人至少两份主食或等价分享餐）。
2. **结构完整**：主食 → 小食 → 饮品，甜品最后补。
3. **丰富优先**：预算内继续增加种类与分量。
4. **低价优先**：满足 1、2 后停止加购。

**不得为了花满预算硬加餐。** 新增餐品必须确实提升体验（人数、饱腹、口味搭配），否则保留余额并说明原因。

### 4. 构造候选组合

用脚本枚举，避免凭感觉凑单：

```bash
python scripts/combo_optimizer.py --input combo_input.json
```

输入 JSON（金额单位**元**，脚本内部按分计算）：

```json
{
  "budget": 30,
  "people": 1,
  "goal": "rich",
  "max_items": 4,
  "require_categories": ["主食"],
  "exclude_keywords": ["牛肉"],
  "max_kcal": 700,
  "items": [
    {"code": "9900014838", "name": "枫糖风味厚松饼猪柳蛋堡三件套",
     "price": 27.9, "origin_price": 39.5, "category": "主食", "kcal": 560}
  ]
}
```

- `goal`：`rich`（默认，丰富优先）或 `cheap`（低价优先）。非法值会报错，不会静默兜底。
- `people`：**硬约束**，必选分类的份数必须满足人数，任何情况下都不放宽。预算买不起足够份数时脚本报错，此时应告知用户「预算内无法满足人数所需份数」，不得降级成一人份推荐。
- `max_kcal`：可选热量上限；`0` 是合法值。**任一菜品缺失 `kcal` 时，该方案热量标记为未核实**；设了上限时未核实方案会被直接排除，不得视为达标。
- `kcal` 必须透传，不得在构造候选时丢弃。
- `category` 需由你把麦当劳原分类（人气热卖、小食拼盘、精选单人餐等）映射到 `主食 / 小食 / 饮品 / 甜品`。映射不上会导致无解并报错，这时应修正映射或显式传 `require_categories`，**不要靠放宽约束出方案**。
- **`exclude_categories`：仍建议传 `["周边"]` 作为双保险，但安全已不再依赖它。** 真实菜单里混有非食品（实测「麦当劳限定丝巾」34.9 元、「薯条脆卜卜毛绒周边」24.9 元），且它们会被嵌进「人气热卖」「小食甜品/其他」等食品分类，只靠调用方做分类映射会漏。脚本侧现在做**确定性识别**（`mcd_common.resolve_category`）：命中已知非食品编码或名称关键词（丝巾/周边/毛绒/玩具/公仔/玩偶/礼品卡/水壶/保温杯/钥匙扣/徽章/手提袋）的条目，无论被标成什么分类一律归 `周边` 并丢弃；返回里的 `non_food_excluded` 是剔除计数，非 0 说明该门店菜单混入了非食品，属正常现象。
- 同理，`require_categories` 里不要出现 `周边`、`多人餐` 这类非餐品或非单人分类。
- `max_quantity`：单品最多份数，缺省等于 `max_items`。同一餐品买多份用这个字段，**禁止用重复记录同一编码来伪造份数**（会直接报错）。
- 重复编码、价格非法、热量为负都会被拒绝或跳过并写入 `invalid_items`；`budget` 为 `NaN`、负数、`people` 为 0、`goal` 非法等直接返回结构化错误。

调用后必须读两个状态字段：

- `truncated`（或细分字段 `candidate_truncated` / `search_truncated`）：候选或搜索被截断，结果只能表述为「已比较方案中更优」，禁止宣称全局最优。
- `price_basis` 恒为 `menu_estimate`，即**预估金额**，不是实付。

脚本输出的是**预估价**，不含满减、运费、随单购与券；只有经 `calculate-price` 的金额才可称「实付」。脚本报错时应把错误原因转告用户，不得自行放宽条件重新推荐。

### 4.1 三选一推荐视图（默认展示方式）

用户要的是「几个选择」，不是一次一个最优解。用 `scripts/plan_compare.py` 在同一份需求上**同时跑三套**并对比，再渲染成三张对照卡片：

```bash
python scripts/plan_compare.py --input combo_input.json
```

它在 `combo_optimizer` 上跑三个 `goal`：

| 视图 | goal | 定位 | 当约束下无解时 |
|---|---|---|---|
| 主推 | `rich` | 丰富优先，省得最多、品类最多样（默认推荐放第一） | 折叠，说明原因 |
| 省钱 | `cheap` | 同样约束下压低预估金额 | 折叠，说明原因 |
| 健康 | `lean` | 同样约束下优先低热量（需菜单有 kcal） | 折叠，说明原因 |

输出含 `views`（三张方案 + 各自「为什么选它」理由）、`diff`（三套**预估价差**与**热量差**、默认推荐）。渲染要点：

- 默认推荐（主推）放第一，其余两张作为对照，并标注三套的差额，让用户按需切换。
- `lean` 的热量只有数据齐全时才可信；`kcal_verified=false` 时理由要明确写「热量数据不全，仅供参考」，不得宣称达标。
- 任一视图无解时，它在 `views` 里该项的 `plan` 为 `null`、并带 `error_code`，**不要当成出错**，照常展示另外两张即可。
- 仍只是预估：券、满减、运费、随单购都会改变实付，最终以 `calculate-price` 为准。

### 5. 券后实付对比：决定「最优惠」的唯一依据

**脚本给出的不是最终答案。** `combo_optimizer` 只用菜单价计算，不含券、满减、随单购、运费、打包费，它的排序只是**候选排序**。真正的「最优惠」必须由 `calculate-price` 的实付金额决定。

流程：

1. 取脚本输出的 top N 候选方案（N 通常 3）。
2. 对每个方案调 `calculate-price`：
   - 先算**不带券**的基准价。
   - 若卡包里有可用券，再算**带券**价（同一个方案可试多张券，取最低）。
3. 用 `scripts/rank_by_actual.py` 合并排序：

```bash
python scripts/rank_by_actual.py --input rank_input.json
```

输入把候选与报价关联起来（`pay` 为实付金额，单位元）：

```json
{
  "goal": "cheap",
  "candidates": [
    {"label": "方案A", "items": [{"code": "9900013304", "quantity": 1}], "estimate": 14.9}
  ],
  "quotes": [
    {"label": "方案A", "pay": 14.9},
    {"label": "方案A", "coupon": "C123", "pay": 11.9, "note": "麦辣鸡腿堡券"}
  ]
}
```

输出按每个方案的**最优实付**升序排列，并给出券前券后差额、预估与实付的偏差。

结果处理：

- **以实付最低者为最终推荐**，哪怕它不是脚本排第一的方案。
- 实付与预估不一致时脚本会告警，此时**必须向用户说明差异**（是出现了预估没算到的优惠，还是有没计入的费用）。
- 用券省下的钱要明确列出，让用户判断是否值得为用券而改变搭配。

### 6. 看凑单信号

`calculate-price` 的 `data.enjoyable` 提示「还差 X 元可减 Y 元」时，先算清是赚还是亏：**加购金额必须小于优惠额才划算**，否则不推荐。低价优先目标下，除非用户同意，不主动凑单。

### 7. 券的来源限制（无法绕过的现实）

- **可领取的券没有 `couponId`**，不能代领，也无法带券试算 → 只能告知券名与门槛，请用户自行领取。
- **只有卡包里的券**（`query-my-coupons`）能带入 `calculate-price`。
- 到店场景**没有独立的满减规则接口**（`query-promotions` 仅企业团餐可用），满减只能从算价结果反推。
- 因此：用户卡包为空时，无法做「券后对比」，此时应如实说明「当前没有可试算的券，以下为未用券价格」，**不得虚构用券后的价格**。

### 8. 输出

1. **结论行**：主推方案 + 实付 + 当前目标（丰富优先 / 低价优先）。
2. **方案表**：菜品 / 现价 / 原价 / 数量 / 小计。
3. **对比说明**：原价合计 vs 实付，省了多少、省在哪。
4. **备选方案**：与主推的差异，多花或省多少，换来什么。
5. **下一步**：确认后算价，再单独询问是否下单。

## 实时无解处理（六类映射，含实时三类）

按 `diff-internal-test-prompts.md` P3，无解必须覆盖六类并给出 `error_code` + 缺口量化 + 可选放宽（仅软目标）。其中**前三类由脚本自动覆盖**（返回 error_code 与缺口，无 `top_plans`），后三类来自实时接口返回，本模式必须显式识别与处理：

| 类别 | 触发来源 | 处理要点 | 覆盖层 |
|---|---|---|---|
| budget_shortage（预算不足） | 脚本求解失败 | 报缺口金额，给可降的软目标建议，不静默降人数/预算 | 脚本自动 |
| kcal_conflict（热量冲突） | 候选被上限排除殆尽 | 说明哪条餐品超上限，建议替换/减少，不静默去掉热量限制 | 脚本自动 |
| category_conflict（分类冲突） | 门店无该分类在售 | 说明缺哪类餐品，修正映射或显式传 `require_categories`，不靠放宽出方案 | 脚本自动 |
| **out_of_stock（缺货）** | `query-meals` 在售 / `canWithOrder` | 标注「当前门店无货」，剔除后重算；若因此缺人数份数，按缺口报，不降人数 | **实时接口** |
| **coupon_unavailable（券不可用）** | `calculate-price` 实付 | 说明券不适用于门店/渠道/门槛，以算价为准剔除该券，不虚构券后价 | **实时接口** |
| **store_restricted（门店限制）** | 门店/履约未验证 | 提示换店或转人工，不承诺未验证门店/履约（R1 边界） | **实时接口** |

### 缺货（out_of_stock）
- 权威来源是 `query-meals` 的实时在售状态与 `canWithOrder` 标记；菜单快照 / fixture 不反映实时库存，不得据此声称「有货」。
- 命中后：把缺货餐品从候选里剔除并重新求解；若剔除后无法满足人数份数或必选分类，按 budget_shortage / category_conflict 报缺口，**不得静默降人数或放宽结构**。
- 切勿把缺货当成「无解但能凑一人份」——人数仍是硬约束。

### 券不可用（coupon_unavailable）
- 以 `calculate-price` 实付为准：券带入后实付没减，就是不适用（门店 / 渠道 / 门槛不符），不要坚持宣称能用。
- 处理：从券后对比中剔除该券，按券前实付或其他可用券重新排序，并明确告知用户「该券当前不适用」。
- 禁止虚构用券后价格（见上文 §7 券的来源限制）。

### 门店限制（store_restricted）
- 触发：用户给的门店码未经过 `query-nearby-stores` / `query-meals` 验证、或 `beType`（堂食 / 外送）组合未验证、或该门店 / 履约方式本身不支持。
- 处理：先重新走标准链（`query-nearby-stores` → `query-meals` → `calculate-price`），无法验证则提示换店或转人工；**不得承诺未验证门店或履约方式**（R1 边界）。
- 门店或履约任一变化时，必须重新拉取菜单与算价，不得复用旧门店的候选。

> 通用护栏：六类无解一律只报告缺口 + 可选放宽（仅软目标），硬约束（预算 / 人数 / 忌口 / 门店在售）永不静默降低；绝不自行「去掉一个人的份数」「把预算调高」「忽略忌口」来凑出方案。

## 判断标准

- 套餐类（三件套/四件套/随心配）通常比单点组合更划算，先查套餐再补单点。
- 同名不同编码的餐品价格可能不同，逐一比对后再选。
- 折扣额（`originalPrice - currentPrice`）是参考，不是唯一标准，不能为凑折扣推荐用户不需要的餐品。

## 与其他模式组合

### 营养 + 预算（最常见）

同一句话里既有预算又有热量要求时，一次调用同时传 `budget` 与 `max_kcal`，不要分两次推荐：

```json
{"budget": 60, "people": 2, "goal": "rich", "max_kcal": 700, "items": [...]}
```

设了 `max_kcal` 后，热量缺失的餐品会被排除；若因此无解，说明热量可核实的餐品买不起或不满足人数，应如实告知并请用户放宽，**不要悄悄去掉热量限制**。

### 券 / 积分 / 活动 + 凑单

用户要求「先看看有什么券再凑单」时：

1. `available-coupons`（可领取）→ `query-my-coupons`（已拥有）→ `query-store-coupons`（当前门店可用）。
2. **可领取的券只返回标题与图片，没有 `couponId`，无法直接带券试算**，也不能代替用户领取。只能告知用户券名与门槛，请他自行领取。
3. 只有**已拥有**的券能带入 `calculate-price` 的 `couponId` / `couponCode`。
4. 券是否真的可用，**一律以算价结果为准**；算价没减就是不适用，不要坚持宣称能用。
5. 有可用券时，给出「用券前 vs 用券后」的金额对比，让用户自己判断是否值得为用券而改变搭配。

积分只用于积分商城兑换，**不得声称积分能直接抵现金**；活动价以当前门店菜单为准。

### 转盘 → 凑单

转盘抽中后用户提出预算或热量要求，立刻改走本模式重新推荐，不要再随机重抽。

## 注意

- 预算是实付上限，不是商品原价上限；外送还要计入配送费与打包费。
- 券的可用性以 `calculate-price` 结果为准，不承诺「一定能用」。
- 随单购、早餐卡、麦金卡等需额外付费的权益，必须单独征得同意并计入总价。

## 6. 优惠券智能组合与省钱解释

目标：把「怎么用券最划算」讲成用户一眼能看懂的账，而不是只给一个结论。

### 执行步骤

1. 读取用户卡包（`query-my-coupons`），只有存在有效券标识时才进行带券试算。
2. 生成无券、用券、凑单和套餐/随单购候选方案。
3. 对每个候选分别调用 `calculate-price` ，按实时实付从低到高排序。
4. 输出商品金额、优惠金额、额外加购金额、配送/打包费用和实付金额。
5. 对凑单方案说明“多花多少钱、节省多少钱、是否值得”，并说明新增商品的实际用途。
6. 券不可用时展示接口返回原因，不自行推断原因。

### 省钱解释标准格式（默认输出）

每个方案必须能回答下面四个问题，缺一项即视为解释不完整：

| 必须回答 | 取值来源 |
|---|---|
| 这一单实付多少 | `calculate-price` 的 price÷100 |
| 比不用券省多少 | 同客单无券方案实付 − 本方案实付 |
| 为了用券多花多少 | 本方案商品小计 − 无券方案商品小计 |
| 值不值 | 节省金额 − 多花金额，为负即不值，须明说 |

额外说明：优惠来自券还是活动、配送/打包费是否变化、随单购会员卡是否计入总价。

### 硬约束

- 菜单价、活动宣传价和脚本计算结果只能称为预估，不能称为实付。
- 只有实时算价返回金额才能定义“最优惠”。
- 门店、渠道、商品、数量、券或费用变化后必须重新算价。
- 不得为凑券推荐用户明显不需要的商品。
- 随单购会员卡等额外付费项目必须单列、计入总价并征得用户同意。
- 券面额不等于实际节省金额；是否可用、能减多少一律以算价返回为准。
- 无法确认券是否可用时，明确告知“以结算时为准”，不提前承诺优惠。
