# 模式六：多人点餐与 AA 配餐

目标：多人不同偏好下给出**一套**组合方案，并把金额分配到每个人。本模式只做推荐与金额估算，**不接入真实支付分账**。

## 触发信号

「三个人一起点」「我们四个人 120 块」「给我和我老婆各配一份」「AA 怎么分」「两个人一个不吃辣」「团队下午茶」。

## 一、收集要素（缺什么问什么，一次问完）

| 要素 | 必填 | 说明 |
|---|---|---|
| 用餐人数 | 是 | 决定主食份数下限，**硬约束** |
| 总预算 | 是 | 实付上限，含配送/打包费，**硬约束** |
| 每人忌口 / 过敏 | 是 | 严格忌口逐人收集，**硬约束** |
| 个人偏好 | 否 | 口味、热量要求、想吃的品类 |
| 公共分享餐 | 否 | 默认允许小食/饮品共享 |
| 分配方式 | 否 | 默认「尽量均摊」，可选「按个人所选计算」 |

规则：

- 已知信息不重复问；缺人数或预算时一次问完，不要逐个追问。
- 忌口档案（`profile.md`）已记录的内容直接应用，只补问缺失成员的忌口。
- 涉及过敏时按 `mode-nutrition.md` 的过敏规则处理，严重过敏不承诺安全。

## 二、执行流程

```
收集要素（人数/预算/逐人忌口/偏好）
   ↓
query-meals 拿当前门店在售菜单
   ↓
【Agent 侧预处理】汇总全组 strict 忌口取并集
   ↓
combo_optimizer.py 传 people=人数 + budget=总预算 + 并集忌口（exclude_keywords）
   ↓
区分个人餐与公共分享餐（个人餐不可共享，分享餐不重复计入）
   ↓
calculate-price 实时算价（总价 + 逐项小计）
   ↓
【Agent 侧分配】按分配方式算每人金额 → 输出一套结论
```

关键分工：**脚本只负责「全组口径」的候选枚举与人数/预算硬约束**；逐人差异、分享餐归属、金额分摊全部由 Agent 在脚本之外完成。原因见下节。

## 二·补、脚本能力边界（先读这里再调脚本）

`combo_optimizer.py` 实际只支持**全组级**约束，**没有逐人维度**（已实测确认）：

| 参数 | 实际语义 | 注意 |
|---|---|---|
| `people` | 必选分类（默认「主食」）份数 ≥ 人数，不放松 | 全局硬约束 ✅ |
| `exclude_keywords` | **全组统一**排除关键词，作用于所有候选 | 无逐人概念 ⚠️ |
| `soft_exclude_keywords` | **全组统一」降权标注 | 无逐人概念 ⚠️ |
| `members` 等逐人字段 | **不存在**，传入会被静默忽略（不报错、不告警） | 禁止依赖 ⛔ |

由此产生两条硬规则：

1. **逐人忌口必须在 Agent 侧预处理**：把「**任何一位成员** strict 的食材」取并集，作为全局 `exclude_keywords` 传给脚本。宁可候选变少，也不能让方案踩到某位成员的忌口。
2. **成员级差异在输出层说明**：脚本产出的方案已避开全组并集忌口；某位成员「其实可以吃辣但被并集排除了」这类信息，由 Agent 在输出里说明「该方案已避开 A 的忌口，B 可任选」，不假装脚本做了逐人处理。

金额分摊同样不依赖脚本：脚本只输出整单预估，**每人金额必须由 Agent 按 `calculate-price` 的逐项小计自行计算**。

## 三、硬约束（不可妥协）

1. **人数**：主食份数不少于人数（用户明确说有人不吃主食时除外），不得静默减人。
2. **总预算**：实付上限，不是商品原价上限；外送场景计入配送费与打包费。
3. **严格忌口**：全组 strict 取并集后硬排除（见「脚本能力边界」），任一成员的绝对不吃项都不得出现在方案里；并集导致某人可选变窄时，在输出层说明。
4. **门店在售**：只推荐当前门店可点的餐品，不跨门店凑。
5. **无解时指出具体成员与冲突条件**：例如「第 3 位成员不吃牛肉，并集忌口后预算内只剩 12 元，而剩余可选主食都在 20 元以上」，给用户调整依据，不静默放宽任一约束。定位由 Agent 完成（脚本只报「预算内无法购齐 N 份主食」的全组口径）。

## 四、公共分享餐的计费规则

- 分享餐（如大薯条、小食拼盘、饮品）**只能计入一次总额**，不得按人数重复累加。
- 输出时明确列出哪些是个人餐、哪些是分享餐，以及分享餐如何分摊。
- 用户要求「分享餐也要算我头上」时按其要求处理，但需说明这与默认规则不同。

## 五、金额分配（两种方式，由 Agent 计算）

| 方式 | 计算规则 | 适用场景 |
|---|---|---|
| **尽量均摊** | （总实付 − 个人加购）÷ 人数，再加个人加购部分 | 默认，关系熟、不想算细账 |
| **按个人所选计算** | 个人餐按个人实付计，分享餐按约定比例分摊 | 想算清、有人点的明显更贵 |

计算口径：

- **每人金额必须由 Agent 按 `calculate-price` 的逐项小计（`data.productList[]`）自行汇总**，脚本不输出任何分摊结果。
- 展示时给出计算式，让用户能复算（如「总实付 118.4，个人餐合计 114.2，分享餐 4.2 由 3 人均摊 1.4 → 每人 38.07 + 各自加购」）。

输出必须包含：

- 每人餐品清单（含分享餐标注）；
- 每人金额（估算或算价后）；
- 总实付与预算差额（超支 / 结余）；
- 分配方式与计算口径说明。

## 六、价格可信度

- 每人金额来自 `calculate-price` 的逐项小计时，可称「实付分摊」。
- 只有脚本或菜单预估价时，必须标「预估」，不得称「实付」。
- 分配后任何条件变化（换店、换餐品、换分配方式）必须重新算价。

## 七、明确边界

- **第一版不接入真实支付分账**：只做推荐与金额估算，不发起收款、不代付、不承诺自动算账。
- **不替用户判断成员关系**：用户说「我、家人、同事」就按用户给的角色记，不推断亲属关系，不自动保存他人长期偏好（见 `profile.md` 授权边界）。
- **不自动拆分订单**：多人下单仍按一个订单走 `mode-order.md` 的确认卡与授权流程；用户要求分开下单时逐单确认。
- 多人场景同样受交易安全契约约束：算价先于下单、两步确认、幂等、写操作授权。

## 八、输出示例结构

```
方案（3 人 · 预算 120 元 · 均摊）
忌口处理：A 不吃辣 → 已并入全组排除（方案内无麦辣系）；B、C 无忌口
个人餐：
  成员A 板烧鸡腿堡套餐   36.9
  成员B 麦辣鸡腿堡套餐   38.9
  成员C 巨无霸套餐       39.9
分享餐：
  大薯条 ×1             14.5
─────────────────────────
实付合计（calculate-price） 118.4 元
个人餐合计 115.7，分享餐 14.5 由 3 人均摊 4.83
每人分摊 38.53 + 39.57 + 39.57（按各自个人餐 + 分享餐均摊）
预算差额 结余 1.6 元
未满足项 无
```

## 九、与其他模式组合

- **多人 + 营养**：按 `mode-nutrition.md` 逐人核对热量目标，营养可信度分级照常标注。
- **多人 + 预算/券**：按 `mode-budget.md` 逐方案算价，券的可用性以算价为准。
- **多人 + 转盘**：转盘只决定个人餐的随机项，人数与预算约束不放松。
