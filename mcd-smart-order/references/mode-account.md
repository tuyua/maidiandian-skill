# 模式四：订单与资产管理

目标：查询历史订单、卡包优惠券、积分账户与营销活动。本模式只读，不涉及下单。

## 分支处理

| 用户意图 | 工具 | 说明 |
|---|---|---|
| 我买了什么 / 历史订单 / 上一单 | `order-list` | 仅餐饮订单；商城订单用 `mall-order-list` |
| 某个订单的状态 / 详情 | `query-order` | 需要订单号 |
| 取消订单 | `cancel-order` | 需用户明确指定订单，且说明可能无法取消 |
| 我有什么券 / 卡包 | `query-my-coupons` | 返回用户拥有的券，**不做可用性校验** |
| 当前门店能用什么券 | `query-store-coupons` | 需要门店与渠道信息 |
| 能领什么券 | `available-coupons` | 麦麦省可领取的券 |
| 我有多少积分 / 过期积分 | `query-my-account` | 积分账户详情 |
| 最近有什么活动 / 这个月有什么 | `campaign-calendar` | 当月营销活动日历，可传 `specifiedDate` 锚定 |
| 积分能换什么 | `mall-points-products` | 积分商城商品 |

## 订单状态码（实测值，优先于接口文档）

接口文档给出的状态码说明与真实返回不一致，**以实测为准**：

| `status` | `orderStatus` | 含义 |
|---|---|---|
| `10` | 待支付 | 已创建订单，尚未支付 |
| `60` | 订单已取消 | 取消成功 |

判定支付与取消结果时读 `query-order` 返回的 `orderStatus` 文案，不要只依赖 `status` 数字，也不要照抄接口文档中的枚举说明。

`expirePayTime` 是支付截止时间，实测为下单后约 15 分钟；超时未支付订单自动失效，无需手动取消。未支付订单的 `pickupCode` 为空。

## 输出规范

- **订单列表**：时间、门店、商品摘要、金额、状态，按时间倒序。
- **优惠券**：券名、适用条件、有效期，并按三类状态区分说明：
  1. **可领取**（`available-coupons`）：尚未拥有，需先领取。
  2. **已拥有**（`query-my-coupons`）：卡包中的券，但接口**不做门店与渠道校验**，不等于当前可用。
  3. **当前门店可用**（`query-store-coupons`）：结合门店与渠道校验后的结果。
  
  三者不可混为一谈；最终是否可用以 `calculate-price` 结果为准。
- **积分**：总额、即将过期的部分（如有）单独标出，提醒及时使用。
- **活动日历**：区分进行中 / 即将开始 / 已结束，并说明订阅状态。

## 与其他模式组合

### 历史订单 → 复购（常用）

用户说「再来一单」「上次那个再来一份」时：

1. `order-list` 取历史订单，展示时间、门店、商品、金额，让用户指认是哪一单（不要猜）。
2. 取该单的 `orderProductList[].productCode` 与当时价格、数量，作为 `past_order`。把当前门店的 `query-meals` 结果作为 `current_menu`。
3. 用 `python scripts/reorder.py` 对照：自动分出**在售 / 已下架 / 涨价**，并产出 `reorder_payload`（仅含仍售项的 code+数量，可直接喂 `calculate-price`）。已下架项给出按名称近似的替代建议；名称有变（`matched_by=name_approx`）的项需向用户确认是否就是同一产品。
4. 用当前门店重新 `calculate-price`——价格与优惠会变，历史金额不能当作当前价格。注意 `reorder_payload.total_now` 只是菜单预估，实付仍需算价。
5. 用户明确授权后再 `create-order`。

复购不是「复制旧订单」，而是「以旧订单为起点重新走一遍点单流程」。`reorder.py` 只是离线对照，不下单、不调接口。

#### 复购前置核价（每次必做）

历史订单里的价格对当下**无效**。复购前必须重新核实以下四项，缺一项就不得直接下单：

1. **在售状态**：`reorder.py` 已分出在售 / 已下架 / 名称近似，已下架项给替代建议，名称近似项先向用户确认。
2. **当前门店**：历史门店与本次门店不同时，重新 `query-meals`；门店不可用时明确告知，不默认换店。
3. **价格变化**：历史金额只是参考，`reorder_payload.total_now` 也只是菜单预估；**必须重新 `calculate-price`** 才知道实付。
4. **券与活动**：当时用的券现在可能已过期或不适配，重新查卡包并试算。

向用户展示时必须说清「比上次多花 / 少花多少」，涨价项单独标出。任一条件变化后重新算价，不沿用旧结论。

### 活动 → 转盘 / 凑单

`campaign-calendar` 找到的新品或活动餐品，可作为转盘或凑单的候选补充，但实际价格与供应以当前门店菜单为准，活动文案价仅供参考。

### 时段与活动感知推荐（现在更适合点什么）

结合当前时间、餐段、活动日历、用户券包、常去门店与在售菜单，生成「现在更适合点什么」的方案。

执行顺序：

1. 用 `mcp__mcd-mcp__now-time-info` 取当前时间，判断餐段（早餐 / 正餐 / 下午茶 / 夜宵）。
2. `campaign-calendar` 取进行中与即将开始的活动。
3. 结合常去门店记忆（`profile.py store show`）与卡包券，生成候选。
4. 输出时说明推荐理由来自哪几项（时段 / 活动 / 券 / 门店在售）。

边界（不可妥协）：

- **活动宣传价不是实付**：活动文案里的价格只能作为推荐参考，最终价格一律以 `calculate-price` 为准。
- **餐段判定不影响硬约束**：早餐时段推荐仍然要满足预算、人数、忌口。
- **不为活动强行加购**：活动存在不等于用户需要该商品；只有当用户目标与该商品匹配时才纳入。
- 活动餐品不在当前门店在售时，明确说「该门店没有这个活动品」，不跨门店凑。
- 用户没提时间相关诉求时，不主动输出时段推荐，避免打扰。

### 券 / 积分 → 凑单

见 `mode-budget.md` 的「券 / 积分 / 活动 + 凑单」：可领取的券没有 `couponId`，无法代领也无法带券试算；积分不能抵现金。

## 只读边界

本模式默认只读。只有 `cancel-order` 属于写操作，必须：用户指定订单号 → 单独确认 → 说明可能已进入制作流程无法取消 → 再执行。支付状态以 `query-order` 结果为准。

## 注意

- `order-list` 只返回餐饮订单，用户问「买的周边 / 商城订单」时要改用 `mall-order-list`。
- 取消订单前确认订单号并告知可能已制作无法取消，不要承诺一定成功。
- 涉及支付状态查询时，引导用户先完成支付再查。
