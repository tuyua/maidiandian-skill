# 模式二：营养配餐

目标：按热量、蛋白质或忌口约束搭配一餐。麦当劳有「500 大卡套餐」分类和营养数据接口，这是本模式的差异化优势。

## 执行流程

### 1. 明确营养目标

- **热量上限**：如「500 大卡以内」「控制在 600 卡」。
- **营养侧重**：高蛋白、低碳水、少钠等。
- **忌口 / 过敏**：不吃牛肉、不吃辣、乳制品过敏、不吃海鲜等。
- **人数与预算**：可选，没有就不限制预算。

用户没给具体数值时，按成人单餐 500–700 大卡的常见区间处理并说明。

### 2. 拉数据

- `list-nutrition-foods`：拿麦当劳常见餐品的营养成分（能量、蛋白质、脂肪、碳水、钠、钙）。**这是配餐的唯一可靠数据源，不要凭常识估算热量。**
- `query-meals`：拿当前门店在售菜单与价格，确保推荐的餐品真的能点。
- 菜单里的「500 大卡套餐」分类可作为快速候选，但仍需用营养接口核对。

### 3. 匹配与筛选

1. 先在营养数据中按热量/蛋白质筛选符合条件的餐品。
2. 再与当前门店在售菜单取交集——营养库里有的餐品不一定当前门店有售。
3. 按忌口过滤：普通口味偏好（不吃辣、不吃香菜）可用名称关键词排除；**过敏原不得用名称关键词判断**，严重过敏时不承诺安全，提示用户向门店核实配料与交叉接触风险。
4. 组合时保证主食 + 蛋白质 + 饮品的结构完整，热量求和不超过上限。
5. 与预算、人数同时出现时，按 `mode-budget.md` 的联合处理规则输出**一套**结论，不要输出两套互相矛盾的推荐。

### 4. 校验并输出

组合确定后调 `calculate-price` 拿真实价格，然后按以下结构输出：

1. **搭配方案**（表格：菜品 / 热量(kcal) / 蛋白质(g) / 价格）
2. **营养合计**：总热量 XX kcal（占目标 XX%）、蛋白质 XX g、脂肪 XX g、碳水 XX g
3. **为什么这么搭**：如「鸡肉类蛋白高脂低，配无糖可乐把热量压在 520 卡，比同价位牛肉堡少 180 卡」
4. **替代选项**：给出 1–2 个可替换项及其营养差异
5. **下一步**：确认后算价

## 匹配现实：营养库只能核实到一小部分菜单（实测）

`list-nutrition-foods` 返回 160 条，但**与门店菜单名称对得上的很少**。实测某门店 69 项菜单只能精确核实 12 项（约 17%），其中**套餐类一项都核实不了**。

典型对不上的情况：

| 菜单名 | 营养库里的名字 | 能否直接用 |
|---|---|---|
| 薯条 | 中薯条 / 大薯条 / 小薯条 / 迷你薯条 | 不能，规格不明 |
| 可乐 | 可乐中杯 / 大杯 / 小杯 | 不能，规格不明 |
| 麦乐鸡 | 麦乐鸡5块 / 麦乐鸡4块 | 不能，份数不明 |
| 麦辣鸡翅 | 麦辣鸡翅-2块 | 不能 |
| 纯牛奶(盒装) | 纯牛奶（盒装）（全角括号） | 仅标点差异，可视为同一项 |
| 三件套 / 随心配 / 乐园餐 | 营养库中无对应条目 | 不能 |

规则：

- 只采用**名称一致**（或仅差全角/半角标点、空格）的条目。
- 「薯条→中薯条」「可乐→可乐中杯」这类**规格不同的不允许替用**——猜错就是给错热量，宁可标未核实。
- 因此**按热量配餐基本只能在单品层面做**：用户要控热量时，优先用单品组合，并明确告知套餐类算不出热量。
- 设了 `max_kcal` 会让候选大幅收缩，这是数据现实，不是脚本故障；若因此无解，应如实说「热量可核实的餐品太少」，不要放宽成估算值。

## 数据缺失的处理（硬性要求）

- 任一菜品在营养接口中查不到对应条目时，该菜品热量标为**未核实**，禁止填 0 或估算。
- 只要方案中有一项未核实，整份方案的营养合计只能标为**未核实**，不得宣称「控制在 500 大卡以内」。
- 营养接口只有常见餐品数据、门店菜单可能有新品，两者取不到交集时明确告知用户，并给出替代建议。

## 营养可信度分级（三级口径）

营养结论必须带可信度标签，用户据此判断能信多少：

| 等级 | 判定条件 | 输出口径 |
|---|---|---|
| **已核实** | 方案中每一项都能在营养库按名称精确匹配 | 可给出具体热量/蛋白质合计，并说明数据来源 |
| **部分核实** | 部分餐品匹配、部分未核实 | 只对已核实项给数值；合计标「部分核实」，未核实项逐项列出 |
| **仅供参考** | 名称相近但规格/份数不一致，或用户接受估算 | 必须显式标注「以下为近似值，规格可能不符」，不得当作达标依据 |

- **严格达标与近似满足必须分开说**：上限 500 kcal 时，合计 498 是严格达标；合计 520 是近似满足（超限），合计含未核实项是无法判定。三者不得混为「达标」。
- 可信度标签与热量数值同时出现在输出里，不允许只给数值不给标签。
- 用户要求「精确到克」而数据只到三级时，如实说明数据粒度，不编造精度。

## 过敏原与交叉接触风险（不可妥协）

- **过敏原不得用名称关键词判断**：菜单名与营养描述都不含完整配料表，「无花生」字样不等于无花生制品。
- 用户声明过敏时：
  1. 按用户提供的过敏原清单做名称级硬排除（已知高风险项）；
  2. 明确告知「名称排除不等于成分确认」；
  3. **严重过敏一律不承诺安全**，提示用户向门店核实配料、共用炸锅/产线的交叉接触风险；
  4. 建议保留门店联系方式，用餐前再确认一次。
- 交叉接触必须主动提及的典型场景：共用炸锅（炸鸡类与薯条）、同一产线分装、酱料含过敏原。
- 不得为了凑方案弱化过敏提示，也不得把「应该没事」当结论。

## 注意

- 营养数据与实际制作存在误差，输出时说明「数据来自麦当劳官方营养信息，实际以门店为准」。
- 忌口涉及过敏时，宁可多问一句也不要猜。
- 热量控制不等于健康建议，不要给出医疗或减脂处方性质的结论。
- 「第二份半价」「第二份优惠」类标签会影响实际单价，算价时以接口返回为准。
