# 模式五：单品套餐转盘

目标：用户「不知道吃什么」时，从当前门店在售餐品里随机抽一个套餐或单品。解决选择困难，不做最优推荐。

## 核心定位：随机，不是推荐

转盘的结果**不代表最划算、最合适或最好吃**。输出时必须说明这一点，禁止用「为你精选」「最优选择」这类措辞。

它的价值在于：把随机性限制在**已过滤的可行集合**里——预算、忌口、热量、分类都先过滤掉，保证抽中的一定能买、能吃，而不是瞎抽一个买不起或忌口的。

## 执行流程

### 1. 确认范围与约束（都能缺省，缺了就不限制）

- **范围**：`mode` = `combo`（只要套餐）/ `single`（只要单品）/ `any`（不限，默认）。
- **预算**：单品价格上限。
- **忌口**：`exclude_keywords`。
- **热量**：`max_kcal`，设了就只保留热量已核实且不超限的餐品。
- **分类**：`categories`，限定主食/小食/饮品/甜品。
- **整类排除**：`exclude_categories`，建议传 `["周边"]`。真实菜单里混着非食品（丝巾、毛绒周边），它们有价格有编码，且会被嵌进食品分类；**脚本已做确定性兜底**——命中非食品编码或名称关键词的条目无论标成什么分类都会被剔除并计入 `non_food_excluded`，因此即使漏传该参数也不会把周边抽给用户。
- **排除**：`avoid`，上一轮已抽中的编码，避免「再来一次」抽到同一个。
- **加权**：`weight_by_discount`，开启后折扣力度大的中签概率更高（默认关闭，纯随机）。

用户没给约束时，默认 `mode=any` 且不限制预算，**但仍要过滤掉超预算餐品**——因为预算是硬约束。

### 2. 拉数据并标注分类

`query-meals` 拿菜单。判定套餐还是单品：

1. **优先用 `tags`**：含「套餐」判为套餐，含「单品」判为单品。
2. **tags 缺失时用名称关键词**：名称含「套餐 / 件套 / 随心配 / 乐园餐 / 分享餐 / 拼盘 / 双人餐 / 多人餐」判为套餐，否则单品。
3. `category` 需你把麦当劳原分类映射到 `主食 / 小食 / 饮品 / 甜品`（同 `mode-budget.md` 的要求）。

### 3. 调用脚本

```bash
python scripts/spin_wheel.py --input wheel_input.json --top 3 --seed 12345
```

`--seed` 用于复现：同一 seed 必得同一结果，便于演示与排查。`--top` 一次抽多个且互不重复，适合给用户「三选一」。

输出含 `pool_size`（候选池大小），**池子很小要主动说明**——比如只剩 2 个可选，随机就没意义了，应提示用户放宽条件。

### 4. 输出

1. **抽中结果**：名称、价格、原价、热量（未核实要标明）、套餐还是单品。
2. **候选池说明**：从 N 个符合条件的餐品中随机抽中，过滤条件是什么。
3. **明确提示**：随机结果，不代表最划算或最合适。
4. **下一步**：不满意可「再来一次」（把本次编码放进 `avoid`）；或转成 `mode-budget.md` 做正式推荐。

## 与省钱凑单的分工

| 场景 | 走哪个 |
|---|---|
| 不知道吃什么、随便、来点惊喜 | 转盘 |
| 有预算想算划算、要控制热量、要服务多人 | 省钱凑单 / 营养配餐 |

转盘之后用户若提出具体条件（「30 以内」「不吃辣」），应切换到对应模式重新推荐，不要继续随机。

## 与其他模式组合

### 活动 → 转盘

用户说「今天有什么活动，随便来一个」时：先 `campaign-calendar` 找新品或活动餐品，把这些餐品作为转盘候选池，让随机落在活动范围内。活动文案价仅供参考，实际价格以菜单与算价为准。

### 转盘 + 预算 / 忌口 / 营养

约束照常生效：传 `budget`、`exclude_keywords`、`max_kcal`、`categories`。转盘只在**过滤后的可行集合**里随机——抽中的一定买得起、能吃，不存在「随机到买不起」的情况。

### 转盘 → 正式推荐

用户抽中后提出具体条件（「30 以内」「热量别太高」），改走 `mode-budget.md` 或 `mode-nutrition.md` 重新推荐，不要继续随机重抽。

## 注意

- 抽中后若用户要下单，**必须重新走 `calculate-price`**，转盘用的是菜单预估价。
- 不要连续多次无约束重抽来「碰运气」，那等于放弃过滤的意义。
- 候选池为空时脚本报错，此时应告知用户放宽条件，不要自行取消约束。
